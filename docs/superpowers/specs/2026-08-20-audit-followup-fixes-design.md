# 审计后续修复设计

**状态：** 已批准  
**批准依据：** 用户在 2026-08-20 明确要求按审计建议顺序执行。  
**范围：** 证据索引呈现、AppTest 隔离、项目状态文档、Git 遗留清理。

## 目标与边界

本轮只处理已经确认的可维护性和展示问题，不改变评分维度、分值、阈值、裁判模型、被测模型提示词、样本专业内容、Supabase 表结构或既有记录。项目继续采用编辑型咨询报告视觉，不引入 SaaS 卡片、渐变、阴影或营销文案。

## 证据索引

证据索引仍使用一条线性的报告记录，但重新建立信息层级：样本编号、模型显示名与入选依据提升为可读元信息；题目保持主标题但不压过评分事实；总分和模型整体最弱维度成为主要事实；五项维度使用现有中文标签与满分显示。原始模型 ID 保留为次级可追溯信息。

`EvidenceItem.weakest_dimension` 的算法继续表示模型在当前正式比较组中的整体最弱维度。界面将其明确写成“模型整体最弱维度”，避免被理解为当前样本单条评分的最弱项。维度分数显示为“专业准确性 20/30”一类文本，不再暴露 `accuracy_score` 等内部字段。

CSS 使用与现有报告标题相同的高特异性 Streamlit 容器选择器，确保题目字号不会再被 Streamlit 的 `h3` 默认样式覆盖。桌面端事实值不小于 16px，元信息不小于 15px；手机端保持单列、44px 操作目标和无页面横向溢出。

## AppTest 隔离

完整应用渲染测试通过共享 fixture 强制 `DATABASE_URL` 指向每个测试的临时 SQLite，并在测试前后清理 Streamlit 数据缓存、结论缓存和 ResultStore URL 缓存。fixture 不触发模型调用，也不读取正式 Supabase secrets。测试记录实际使用的 engine URL，证明完整应用渲染只访问临时数据库。

## 文档状态

`docs/extension_roadmap.md` 改为当前事实：真实回答、自动评分、PostgreSQL/Supabase 增量持久化和正式结论链路已经验证；下一阶段是扩充样本覆盖与评分一致性。两份已实施计划在顶部增加完成状态、完成提交和“复选框为执行清单历史”的说明，不机械改写全部步骤。

## Git 清理

唯一未合并视觉实验先创建带说明的 archive tag，再删除其干净 worktree与本地分支。其余干净且已合并 worktree、已合并本地分支和已确认过时的 stash 按顺序清理；执行分支与 `.claude/` 不在删除范围。所有删除动作都在实现提交与全量验证之后进行。

## 验收标准

- 证据索引不显示 `_score` 内部字段；中文标签和满分与现有 metrics 配置一致。
- “模型整体最弱维度”语义明确，算法与记录不变。
- 真实 DOM 中题目约 22–24px，元信息至少 15px，事实值至少 16px。
- 390×844 与 320×844 无页面横向溢出，三个证据操作保持可达。
- 两个 AppTest 不读取正式 Supabase，重复运行稳定。
- 全量 pytest、Ruff、py_compile、diff-check 通过。
- Supabase 运行表行数不变，浏览器验证不触发模型或数据库写入。
