# 证据优先的专业模型评测报告设计

**日期：** 2026-08-13  
**状态：** 已完成交互式设计确认，待实施计划  
**适用项目：** FinDueEval MVP

## 1. 背景

当前项目已经具备专业样本、模型回答、AI 评分、评测结论、PostgreSQL／Supabase 增量持久化和中断恢复能力，但页面仍容易被理解为一个评测 SaaS 或管理后台：结论不是默认入口，首页和移动端存在较多卡片式组件，发起评测与数据维护过于突出，模型回答与评分仍是两个需要人工衔接的阶段。

本轮优化面向“专业领域数据产品经理（小语种、医学法律等学科）”岗位。面试官在约 60 秒内应首先感受到：项目结论可信，结论能够追溯到专业标准答案、模型回答和评分理由；工程能力用于支撑证据与可靠性，不抢夺展示主线。

## 2. 设计目标

1. 将评测结论设为默认首页，让面试官先获得判断，再按需验证证据。
2. 建立从模型判断到评分维度、代表样本、专业标准答案、模型回答和评分理由的完整追溯链。
3. 采用中文研究简报／精品咨询报告的编辑式视觉语言，移除 SaaS Dashboard 和 AI 模板感。
4. 将审阅内容与评测操作分层，保留公开操作能力，但不让维护入口打断阅读。
5. 将“生成回答”和“AI 评分”合并为一次自动评测；用户不再二次确认是否评分。
6. 让评测批次可增量持久化、可安全恢复、可避免重复写入，并在持久化失败时停止后续 Token 调用。
7. 统一正式数据口径；历史演示记录保留但永久隐藏和排除，不再提供演示模式。

## 3. 非目标与约束

- 不修改评分模型、评分维度、评分阈值、提示词或裁判模型配置。
- 不修改样本内容、专业标准答案、模型回答、项目定位、方法说明或已有结论文案。
- 不将当前样本范围内的结论包装为通用模型排行榜。
- 不增加登录或权限控制；线上继续允许公开发起真实调用，既有 Token 成本与数据污染风险保持不变。
- 不删除既有正式回答、正式评分、批次或结论数据。
- 不删除历史演示记录；它们只是不再进入任何产品读取路径。
- 不引入新的外部服务。
- 本设计原则上复用现有数据库表；如实现中发现现有约束不足，必须先回到规格评审，不得直接扩张数据库范围。

## 4. 核心设计原则

### 4.1 先给结论，再给证据

默认浏览主线为：

`执行摘要 → 模型判断 → 证据索引 → 代表样本 → 完整评测记录`

项目说明不再作为进入结论的门槛，而是用于按需验证方法和边界。

### 4.2 页面本身就是报告

视觉秩序依赖标题、编号、网格、细分隔线、留白和正文层级，不把报告装进一张大卡片。交互只负责查证，不负责制造视觉热闹。

### 4.3 阅读与运行分离

Streamlit 页面只负责呈现和发出用户意图。模型调用、自动评分、增量持久化和批次状态由独立评测编排器负责；结论与详情由统一读取模型产生。

### 4.4 正式数据口径唯一

结论、计数、模型判断、回答明细和导出必须经过同一正式记录策略，避免页面分别过滤数据造成口径漂移。

## 5. 信息架构与导航

### 5.1 默认入口

应用默认进入 `评测结论`，不再默认进入 `项目说明`。

### 5.2 导航分层

主导航只包含审阅页面：

`评测结论｜项目说明｜样本库`

`评测操作`位于视觉权重更低的次级入口，承载：

- 开始或继续评测；
- 运行批次与技术明细；
- 数据导入、导出等维护能力；
- 样本维护的关联入口。

数据维护和样本维护仍可在相关页面通过次级文字入口到达，但不作为默认页面的主按钮。

### 5.3 面试审阅节奏

- **0–15 秒：** 在评测结论首屏看到执行摘要、样本范围、模型当前判断和结论边界。
- **15–40 秒：** 从模型判断进入评分维度、代表样本、标准答案、模型回答和评分理由。
- **40–60 秒：** 按需进入项目说明，验证项目定位、样本方法、评分口径和适用范围。
- **继续探索：** 在样本库查看 13 个专业任务的完整档案，或进入评测操作查看真实运行能力。

## 6. 视觉基线

### 6.1 保留

- 暖纸色背景、深色正文、克制的棕金强调色；
- 中文衬线标题和高可读正文；
- 章节编号、细线、报告注释与页边信息；
- 既有项目标题、说明和专业文案原文。

### 6.2 删除或避免

- 首页圆角内容卡和大面积投影；
- KPI 侧栏、仪表盘、置信度仪表和装饰性图表；
- 胶囊标签、渐变、图标堆叠和状态徽标墙；
- 英文装饰眉题和新造的 AI 营销口号；
- 为桌面表格另造一套手机卡片业务逻辑；
- 非操作页面的大按钮和固定操作栏。

### 6.3 响应式规则

- 桌面端使用报告网格和高密度审阅表。
- 手机端对同一语义结构做纵向重排，不创建独立卡片数据源。
- 320px、390px、768px 和桌面端均不得出现页面级横向溢出。
- 原始代码块或原始数据表可以在局部容器内横向滚动。
- 真正可操作的控件继续满足至少 44px 触控高度。

## 7. 评测结论页

### 7.1 首屏

首屏依次呈现：

1. 项目现有标题和说明；
2. 动态评测范围元数据，如专业样本数、模型数、正式评分数和正式数据口径；
3. 现有执行结论原文；
4. 与结论直接关联的主要评分维度、代表样本和方法边界入口。

元数据是报告注释，不使用 KPI 卡片。不得增加数据无法证明的“AI 置信度”或营销判断。

### 7.2 模型判断

保留现有字段和排序规则：

- 模型；
- AI 评分样本数；
- 平均分；
- 当前判断；
- 主要依据。

桌面端显示为审阅表；手机端按同一行结构纵向重排。选择模型后定位到该模型的证据索引，不跳回页面顶部。

### 7.3 证据索引

证据链固定为：

`模型判断 → 评分维度 → 代表样本 → 原始回答`

每个代表样本提供三个并列查证入口：

- 专业标准答案；
- 模型回答全文；
- 评分理由。

默认优先列出最能支撑当前判断的代表样本，同时保留查看全部记录的能力。代表样本的选择只能依据现有评分和错误信息，不得新造结论。

## 8. 项目说明页

- 页面继续完整保留现有项目定位、方法、范围和限制文案。
- 不新增营销口号或泛化能力主张。
- 使用报告章节和正文排版，不使用状态卡、领域标签墙或功能卖点卡。
- 作为结论的“方法附录”，通过页内目录快速到达评测方法、样本构成、评分口径和结论边界。

## 9. 样本库

### 9.1 默认视图

样本库改为“专业样本索引”：

- 以编号、完整标题、场景和状态构成审阅目录；
- 筛选器压缩为关键词、场景和“更多筛选”；
- 默认任务是阅读和核验，不是新增或编辑数据；
- 样本维护通过次级文字入口进入。

### 9.2 样本档案

选中样本后，以同一档案目录切换：

- 任务与模拟数据；
- 专业标准答案；
- 质量要求；
- 评审重点。

所有内容保持原文，不把长文本分别包进多张圆角卡片。

## 10. 单入口自动评测

### 10.1 产品行为

评测操作页只保留一个新批次入口：`开始评测`。

用户只配置：

- 专业样本范围；
- 评测模型；
- 现有真实调用参数。

开始评测即代表运行完整链路，评分是评测定义的一部分。页面不再出现：

- 演示模式；
- 真实／演示模式切换；
- “生成 AI 评分”按钮；
- 是否需要评分的二次确认；
- 演示评分恢复入口。

### 10.2 单条任务处理顺序

每个“样本 × 模型”任务按以下顺序处理：

1. 将回答队列项标记为运行中；
2. 调用评测模型；
3. 持久化回答或回答失败记录；
4. 若回答成功，创建或恢复对应评分队列项；
5. 自动调用现有评分模型，无需人工确认；
6. 持久化评分结果或评分失败记录；
7. 刷新批次状态和正式结论读取模型；
8. 继续下一个任务。

回答调用失败时，持久化失败状态并继续其他任务。评分调用失败时，保留成功回答、持久化评分失败状态并继续其他任务。

任何回答或评分的数据库写入失败时，立即停止后续模型调用，避免在无法保存结果的情况下继续消耗 Token。

### 10.3 批次与评分批次关系

- 每次开始评测生成一个 `run_id` 和一个对应的 `score_run_id`。
- 回答通过现有唯一键 `(run_id, case_id, model_name)` 幂等写入。
- 评分通过现有唯一键 `(score_run_id, case_id, eval_model)` 幂等写入。
- 评分队列行携带 `run_id`，恢复时可从评测批次找到对应评分进度。
- 成功记录不得因页面重跑、网络重试或继续评测而重复调用或重复写入。

## 11. 批次状态与恢复

### 11.1 互斥批次状态

页面同一区域只显示一个批次状态：

- **运行中：** 仍在生成回答、自动评分或持久化。
- **已完成：** 全部计划项均成功回答、评分并保存。
- **部分完成：** 至少一项正式评分成功，但存在回答或评分失败。
- **已中断：** 进程已结束，数据库中仍有可恢复的未完成项。
- **已停止：** 持久化失败，系统已停止后续 Token 调用。
- **失败：** 没有产生任何可进入正式结论的评分。

批次状态必须同时考虑回答队列和评分队列；不能仅因回答完成就标记整批已完成。

### 11.2 中断恢复

- 页面重新打开后从 `live_evaluation_runs`、`live_run_queue`、`live_run_responses`、`live_score_queue` 和 `live_run_scores` 恢复进度。
- 访问页面不会自动继续产生 Token。
- 已中断批次显示已完成、失败和剩余数量，并提供唯一恢复动作 `继续评测`。
- `继续评测`只处理原批次未完成项；已成功回答和已成功评分不重新调用。
- 续跑前校验数据集、样本、模型、提示词、生成参数和评分参数哈希；不一致时禁止将新结果混入旧批次。
- 数据库恢复后，因持久化失败而停止的批次可通过同一 `继续评测`动作恢复。

### 11.3 并发领取

为避免多个 Streamlit 会话同时续跑同一批次，恢复动作必须对 `live_evaluation_runs.status` 做原子条件更新。只有成功将 `interrupted` 或 `stopped` 转为 `running` 的会话可以执行模型调用；其他会话只读展示最新进度。

长期未更新的 `running` 批次可根据既定超时阈值派生为 `interrupted`。任务每次成功或失败持久化时更新批次时间戳，作为运行心跳。该方案复用现有状态和更新时间字段，不新增数据库表。

## 12. 正式数据与历史演示记录

新增统一的 `FormalRecordPolicy`，成为结论、统计、详情、导出和恢复的唯一过滤边界。

正式评分至少满足：

- `judge_status == success`；
- 记录状态有效；
- 不属于 mock／demo 运行；
- 不属于 skipped、inactive 或其他排除状态；
- `case_id` 属于当前有效样本范围；
- 对应模型回答属于真实调用。

历史演示记录：

- 保留在数据库中，不做物理删除；
- 不出现在任何页面、计数、结论、模型判断、导出或恢复入口；
- 不允许被新评测流程继续生成；
- 演示导入／恢复功能从产品代码路径移除；
- 自动测试可以使用内存假模型或测试数据库，但不得把测试记录写入正式 Supabase。

## 13. 内部架构

### 13.1 报告界面层

职责：渲染执行结论、证据索引、样本档案和运行工作底稿；保存页面选择和滚动请求。

禁止：直接调用模型、直接组织数据库事务、用 Session State 作为运行结果真源。

### 13.2 `EvaluationWorkflow`

新增内部评测编排器，提供最小接口：

```python
start_evaluation(config) -> EvaluationRunRef
continue_evaluation(run_id) -> EvaluationRunRef
load_evaluation_status(run_id) -> EvaluationRunStatus
```

编排器负责回答队列、自动评分、持久化失败停止、状态归并和安全续跑。模型提供者、评分器和持久化仓储继续作为可替换依赖，便于使用假实现测试。

### 13.3 `ResultRepository`

在现有 `ResultStore` 基础上集中提供：

- 初始化回答批次和队列；
- 幂等保存回答；
- 初始化或恢复评分队列；
- 幂等保存评分；
- 归并回答与评分状态；
- 原子领取中断批次；
- 记录和清除持久化错误。

### 13.4 `ConclusionReadModel` 与 `EvidenceIndex`

`ConclusionReadModel`只读取经过 `FormalRecordPolicy` 的样本、回答和评分，产生：

- 动态覆盖统计；
- 模型当前判断；
- 使用边界；
- 主要依据；
- 代表样本索引。

`EvidenceIndex`将每项模型判断连接到现有评分维度、评分理由、专业标准答案和原始模型回答。它是只读投影，不修改评分或结论。

## 14. 模块重构边界

### 14.1 `src/ui/test_run.py`

当前文件约 3500 行，应拆为：

- 评测配置视图；
- 运行进度视图；
- 批次结果视图；
- 页面级协调器；
- 独立的 `EvaluationWorkflow` 服务。

页面代码只组织展示和用户意图，不继续维护回答／评分双阶段状态机。

### 14.2 `src/ui/components.py`

当前文件约 1600 行，应拆分报告排版原语和操作控件原语，删除重复的卡片变体，统一响应式规则。

### 14.3 样本与结论读取

不同页面不得重复实现正式记录过滤、覆盖统计和模型名称映射。相关逻辑集中到 `FormalRecordPolicy`、`ConclusionReadModel` 和 `EvidenceIndex`。

### 14.4 Session State

Session State 只保存：

- 当前页面；
- 当前选中模型或样本；
- 待消费滚动请求；
- 非持久化的表单编辑状态。

批次、队列、回答、评分和持久化状态全部以数据库为真源。

## 15. 错误处理

- **模型回答失败：** 保存失败状态，不评分该回答，继续其他任务。
- **评分调用失败：** 保留回答，保存评分失败状态，继续其他任务。
- **回答或评分持久化失败：** 批次进入已停止，停止后续 Token 调用。
- **数据库读取失败：** 审阅页显示明确不可用说明，不用空数据伪装“暂无结果”；操作页禁用开始和继续评测。
- **配置哈希不一致：** 禁止续跑旧批次，只允许查看既有进度或开始新批次。
- **并发续跑冲突：** 未取得批次领取权的会话保持只读，不执行模型调用。
- **部分完成：** 已成功评分进入正式结论，失败项保持可审计；结论覆盖统计反映实际成功范围。

## 16. 测试与验收

### 16.1 自动测试

按 TDD 实施，至少覆盖：

- 默认首页与审阅／操作导航分层；
- 单一“开始评测”入口，不存在独立评分或演示模式入口；
- 成功回答持久化后自动评分；
- 回答失败后继续其他任务；
- 评分失败后保留回答并继续其他任务；
- 任一持久化失败后不再调用模型；
- 回答与评分幂等键阻止重复写入和重复调用；
- 批次状态由回答和评分队列共同归并；
- 重启恢复、哈希校验和原子领取；
- 历史演示记录在页面、统计、结论和导出中永久排除；
- 结论与证据索引使用同一正式记录口径；
- 手机端纵向重排不产生第二套业务逻辑。

所有流程测试使用假模型、临时 SQLite 或隔离测试库，不触发真实模型调用，不写入正式 Supabase。

### 16.2 浏览器回归

使用 Ego Browser 检查 1710×1009、768px、390×844 和 320px：

- 默认进入评测结论；
- 主导航只有评测结论、项目说明和样本库，评测操作为次级入口；
- 无页面级横向溢出；
- 首页无圆角卡片墙、KPI 侧栏或 AI 营销组件；
- 结论可以逐层进入证据索引和原始记录；
- 样本索引与样本档案在手机端可完整阅读；
- 评测操作页只有一个新批次主动作；
- 已中断批次只在点击继续评测后恢复；
- 浏览器回归不得点击真实评测、导入、保存或删除。

### 16.3 数据不变量

- 实施视觉和结构调整后，既有正式样本、回答、评分和结论数量不变。
- 历史演示记录数量不因本次实施减少，但所有产品读取结果均为零。
- 只有用户主动开始或继续真实评测时，正式回答和评分数量才允许增长。
- 每个正式评分都能追溯到同一 `run_id` 下的真实模型回答和有效样本。

## 18. 已确认决策

- 目标岗位：专业领域 AI 数据／模型评测产品经理。
- 60 秒首要感受：结论可信。
- 首页优先信息：决策摘要。
- 默认首页：评测结论。
- 产品模式：审阅优先。
- 视觉语言：中文研究简报，不采用 SaaS Dashboard 卡片。
- 证据链：模型判断 → 评分维度 → 代表样本 → 原始回答。
- 导航：审阅层与评测操作层分开。
- 评测：一次开始后自动完成回答、评分和持久化。
- 部分失败：成功项继续自动评分并保存，批次标记部分完成。
- 演示模式：删除；历史演示记录保留但永久隐藏和排除。
- 中断恢复：用户主动点击继续评测，不因打开页面自动产生 Token。
