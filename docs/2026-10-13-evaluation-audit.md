# 评测可信度审查与最小实施方案

## 现状（修改前）
- 已有：13 个专业样本、白名单被测输入、裁判独立输入、五维 100 分评分、自动结论、SQLite/PostgreSQL 结果存储、完整队列、中断恢复、数据/Prompt/配置哈希、正式与示例数据隔离、评分导入导出、证据浏览。
- 重复需求：无需重新开发上述功能，成功AI评分继续直接形成结论。
- 缺口：越界评分被 clamp；缺少逐要点评价及引文验证、原始响应；按各自成功样本汇总无法公平比较；最终响应覆盖重试用量；评分导出不能独立回放；缺少独立裁判自测。
- 主要风险：旧记录缺少证据元数据不可补造；有限重试增加费用；历史版本不能拿当前题目伪装运行时题目；不完整 Token 用量不能当零；公开导出需排除密钥、路径；少量裁判自测不能证明全面可靠。
- 当前本地 live_* 表均为空。data 中示例结果不是实际模型运行记录。
- 基线：777 passed, 7 skipped（离线）。

## 最小方案及文件职责
1. `scorer.py` + `score_evidence.py`：严格整数范围与逐维理由；按原有 Gold 生成稳定要点 ID；逐要点评价/引文原文匹配；有限格式重试；保存原始响应与异常。固定公式验证仅适用于输入一致的内置案例，不调整原有权重。
2. `schema.py` / `result_store.py` / `run_checkpoint.py`：添加可空 JSON 字段和独立请求尝试表；兼容 ALTER migration；保存运行时任务/Gold/Prompt；每次返回即持久化尝试。
3. `comparison.py` / 结论读模型和 UI：复用现有 cohort 签名；共同有效任务质量均分；保留全部正式证据；运行分母及失败分别统计；低样本不形成排名结论。
4. `judge_selftest.py` / UI：财务、法律、投行各三个人工固定回答；显式按钮触发，最多 9 次裁判请求、禁用重试；独立文件与会话结果，导出结果，不写正式表。
5. `snapshot.py` / UI：完整证据快照，严格结构/关联/敏感信息检查，只读加载不写数据库不调用 API；缺少真实结果时展示空状态。
6. P0 回归通过后：`request_audit.py` / `runtime_metrics.py` 记录全部尝试及未知用量；价格由用户显式提供来源、币种、生效区间；区分回答/评分估算。P2 可选变体暂不扩展；修正信息不足时强制确定结论的提示边界。

## 验证顺序
- 先写针对缺口的失败测试，再最小实现；API 仅 Mock。
- 运行评分、存储迁移、隔离、公平比较、快照零调用、自测隔离、尝试记录与成本覆盖的测试。
- 全量 pytest、ruff、数据验证、Streamlit AppTest；比对原始 data 文件及本地 DB 的 SHA-256。
- README 和交付报告准确披露离线验证、真实 API 未验证、旧记录边界与人工操作。
